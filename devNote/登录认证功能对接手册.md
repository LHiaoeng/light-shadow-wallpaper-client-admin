# 登录认证功能对接手册

本文档基于当前前端项目代码实现编写，用于前后端联调登录认证功能。

## 1. 对接范围

- 登录方式：账号密码登录（已实现）、手机号登录（UI 有入口，未完成提交逻辑）
- 验证码：滑块验证码（可通过配置开关控制）
- 认证协议：OAuth2 Token 模式（`/oauth2/token`、`/oauth2/revoke`、`/oauth2/check_token`）
- 会话承载：`Bearer access_token`
- 权限加载：登录后通过菜单接口拉取动态路由

## 2. 前端关键配置

### 2.1 环境变量

- `VITE_API_URL`：接口前缀，默认 `/api`
- `VITE_API_TIME_OUT`：请求超时时间
- `VITE_PASSWORD_SECRET_KEY`：密码 AES 加密密钥（登录提交前用于前端加密）

### 2.2 开发代理

`vite.config.ts` 中将 `^/api` 代理到后端服务（默认 `http://127.0.0.1:8080`），并去掉 `/api` 前缀再转发。

### 2.3 登录验证码开关

`src/config/index.ts`：

- `enableLoginCaptcha = true` 时，登录前必须先完成验证码校验，前端把 `captchaId` 传给登录接口。

## 3. 认证整体时序

1. 用户在登录页输入账号密码。
2. 前端将密码用 `AES/CBC/Pkcs7`（`key=iv=VITE_PASSWORD_SECRET_KEY`）加密后提交。
3. 若启用验证码：先调验证码校验接口，通过后拿到 `captchaId`，再调用登录接口。
4. 登录成功后，前端保存：
- `access_token` 到本地存储；
- 用户信息 + `roleCodes` + `permissions` 到本地存储。
5. 前端跳转到目标页（优先 `redirect` 参数，否则 `/`）。
6. 路由守卫首次进入受保护页面时，请求菜单接口并动态注册路由。

## 4. 接口对接明细

## 4.1 验证码接口

### 4.1.1 获取验证码

- 方法：`GET`
- 路径：`/captcha/tianai/gen`
- Query：
- `type`（可选）
- 返回（示例结构）：

```json
{
  "id": "captcha-id",
  "captcha": {
    "backgroundImage": "base64/URL",
    "templateImage": "base64/URL",
    "backgroundImageWidth": 300,
    "backgroundImageHeight": 150,
    "sliderImageWidth": 50,
    "sliderImageHeight": 50,
    "data": {
      "randomY": "..."
    }
  }
}
```

### 4.1.2 校验验证码

- 方法：`POST`
- 路径：`/captcha/tianai/check?id={captchaId}`
- Body（JSON）：
- `bgImageWidth`
- `bgImageHeight`
- `templateImageWidth`
- `templateImageHeight`
- `startSlidingTime`
- `endSlidingTime`
- `trackList`（滑动轨迹）
- 返回：`boolean`（`true` 通过，`false` 失败）

校验通过时，前端将 `captchaId` 传递给登录接口参数 `captchaId`。

## 4.2 登录接口

- 方法：`POST`
- 路径：`/oauth2/token`
- Header：
- `Authorization: Basic dWk6dWk=`（固定客户端凭证）
- 参数提交方式：Query Params（不是 JSON Body）

账号密码登录参数：

- `grant_type=password`
- `username`
- `password`（前端已加密密文）
- `captchaId`（启用验证码时传）

手机号登录参数（预留）：

- `grant_type=mobile`
- `mobile`
- `captcha`

登录成功返回结构（前端当前期望）：

```json
{
  "access_token": "xxx",
  "expires_in": 7200,
  "refresh_token": "xxx",
  "scope": "all",
  "token_type": "bearer",
  "info": {
    "userId": 1,
    "username": "admin",
    "type": 1,
    "organizationId": 1,
    "nickname": "管理员",
    "avatar": "..."
  },
  "attributes": {
    "permissions": ["sys:user:list"],
    "roleCodes": ["ADMIN"]
  }
}
```

注意：该接口返回被前端当作“直接对象”处理，不走统一 `ApiResult<T>` 解包。

## 4.3 Token 校验接口

- 方法：`POST`
- 路径：`/oauth2/check_token`
- Header：`Authorization: Basic dWk6dWk=`
- Query：`token={accessToken}`

## 4.4 注销接口

- 方法：`POST`
- 路径：`/oauth2/revoke`
- Header：`Authorization: Basic dWk6dWk=`
- Query：`token={accessToken}`

前端在注销成功后清理本地用户态并跳转登录页。

## 4.5 登录后菜单接口（权限路由）

- 方法：`GET`
- 路径：`/system/menu/router`
- Header：自动携带 `Authorization: Bearer {accessToken}`
- 返回：当前登录用户菜单路由树数组，用于前端动态生成路由

## 5. 请求头与拦截器约定

## 5.1 请求拦截

前端自动补充：

- `Authorization: Bearer {accessToken}`（当本地有 token 且请求头未显式设置）
- `Accept-Language`（国际化语言）

## 5.2 响应异常处理

- `400`：登录页外弹错误提示
- `401`：清空本地登录态，弹窗提示“登录已过期”，确认后跳转登录页，并带 `redirect`
- `403`：提示无权限访问
- 其他：统一网络异常提示

## 6. 本地存储约定

存储前缀：`breadj-admin/`

- `breadj-admin/access-token`
- `breadj-admin/user-info`

`user-info` 内容为：

- 基础用户信息（`info`）
- `roleCodes`
- `permissions`

## 7. 路由守卫约定

- 未登录访问匿名白名单外页面：跳转 `/login?redirect=目标地址`
- 已登录访问 `/login`：重定向到 `/`
- 已登录首次访问业务路由且无菜单缓存：请求 `/system/menu/router`，动态挂载后重新进入目标路由

## 8. 后端联调检查清单

- `/oauth2/token` 是否支持 `POST + query params` 方式
- `/oauth2/token` 是否校验 `Basic dWk6dWk=`
- 密码解密算法是否与前端一致（AES/CBC/Pkcs7，`key=iv=VITE_PASSWORD_SECRET_KEY`）
- 启用验证码时，`captchaId` 是否参与登录校验
- 登录返回字段是否包含 `access_token/info/attributes.permissions/attributes.roleCodes`
- `/system/menu/router` 是否基于登录态返回当前用户菜单
- `401/403` HTTP 状态码是否正确返回（不要全部返回 200）

## 9. 已知现状与建议

- 手机号登录组件当前仅有表单 UI，尚未实现 `doLogin` 提交逻辑；若需启用，请补齐前端实现并与后端确认短信验证码接口。
- 前端预留了 `refresh_token` 字段，但当前未实现自动刷新 token 逻辑；如需长会话，建议新增刷新流程与失效策略。
